# Cosmic Portfolio — customization playbook

This is a **static HTML/CSS/JS single-page site** (no build step to serve it —
`index.html` + `assets/css/style.css` + `assets/js/main.js`, GitHub Pages).
Read `CLAUDE.md` first for the file map and commands; read `HANDOFF.md` for
the running changelog and a "perfect prompt" description of the whole site.
This skill is the narrower how-to for working *in* this specific codebase.

## Golden rule: content vs. code are different files

- **Never hand-edit `assets/js/projects.js`.** It's generated by
  `python3 tools/build.py` from `src/portfolio.md` (projects/research/
  bolsas/contacts, 4 languages via 🇧🇷🇺🇸🇪🇸🇫🇷 flags) + `src/interface.yaml`
  (UI strings). The git `pre-commit` hook regenerates it automatically.
  If a task is "change what a project card says" — edit `src/portfolio.md`,
  then run `python3 tools/build.py`.
- Everything *interactive* (the sector router, HUD, easter eggs, quests,
  audio, 3D) is hand-authored in `assets/js/main.js` and `assets/js/
  space-3d.js` — edit those directly.

## Where things live in `main.js`

One IIFE, ~5000+ lines, organized into numbered `/* N. SECTION NAME */`
comment blocks — `grep -n "^\s*[0-9]\+\.\?[0-9]*\. [A-Z]" assets/js/main.js`
to see the current map. Roughly: SVG icons → SFX synth → toasts → cinematic
intro → warp-travel engine & sector dossier router → cosmos background canvas
→ cursor/spotlight → dossier content rendering → project modal → spectrum
simulator → command palette & secret cheats → stat counters → quest tracker
→ persistent HUD & floating easter eggs → i18n → init.

Adding a new "sector" (a 5th planet/dossier) means: a new `data-open-sector`
value wired through `initSectorNavigation`, a `WARP_DESTINATIONS` entry, a
new `.dossier-panel` in `index.html`, i18n keys (`kickers.setorNN`,
`titles.setorNN`), and — if it should get a 3D planet during warp — a new
`create3DXGroup()` in `space-3d.js` plus a `planetGroups` entry in
`initWarpScene`.

Adding a new floating easter egg: add an entry to `FLOATING_EASTER_EGGS_LIST`
(needs `id`, `icon`, `name`, `desc`, `action`) — `name`/`desc` are shown
*after* discovery (an `.egg-label` under the icon + the button's `title`),
never before. Map it in `eggWidgetMap` inside `renderFloatingEasterEggs` if
it should reveal a specific `.easteregg-widget` by id.

## Hard-won CSS rules for this codebase (verified today, don't reintroduce)

1. **No hover-to-reveal for primary controls.** The sector-dossier close
   button and the top-bar language switcher were both built as
   `opacity:0; transform: translateY(-N%)`, shown only on `:hover`/
   `:focus-within`. Unreachable on touch, unreliable on desktop, and once it
   gated the *only* close button, the whole router could get stuck (every
   later click landed on the still-open overlay). Any nav/close control must
   have a permanently-visible affordance.
2. **Don't animate `transform` on an ancestor of a `position:fixed`
   element you need pinned to the true viewport.** Chromium keeps treating
   an element as a new containing block for fixed descendants for as long as
   a `forwards`-filled transform animation is attached to it — even once it
   resolves to an identity/`none` value. If you need an entrance animation on
   something that wraps fixed-position content, animate `opacity` only.
3. **Don't rely on `margin: 0 auto` to center a flex item that might have
   zero in-flow children.** Flex auto-margins shrink-to-fit the item's
   in-flow content before centering it; a panel whose only child is
   `position:fixed` (contributes nothing to that calculation) collapses to
   `width:0`. Give such elements an explicit `width: 100%`.
4. **`html, body { overflow: hidden }` is intentional here** (no page-level
   scroll/scrollbars) — which also means the bugs above clip silently with
   no visual hint (no scrollbar, just missing content at the edge). Don't
   trust a screenshot alone; measure (`el.getBoundingClientRect()`,
   `document.documentElement.scrollWidth`) via a quick Playwright script.
5. **Theme is permanently dark.** There is no light mode and none should be
   reintroduced — don't add `[data-theme="light"]` rules or a toggle button
   back.
6. Any "starting value" shown in the UI (e.g. the HUD money counter) tends to
   be set in *two* places — the JS variable default and the initial
   `innerHTML` template string. Grep for the literal value when fixing one.

## Verifying changes: use Playwright, not eyeballing

`playwright` is a local devDependency, not global — run scripts with
`NODE_PATH=$(pwd)/node_modules node your_script.js`, against a plain local
server (`python3 -m http.server 8123`). Minimal pattern for any layout/nav
fix:

```js
const { chromium } = require('playwright');
(async () => {
  const browser = await chromium.launch();
  const page = await (await browser.newContext({ viewport: { width: 1600, height: 900 } })).newPage();
  await page.goto('http://localhost:8123/index.html');
  try { await page.locator('.btn-skip-intro').click({ timeout: 4000 }); } catch (e) {}
  await page.waitForTimeout(1200);
  // ...interact, then measure — don't just screenshot:
  const overflow = await page.evaluate(() => document.documentElement.scrollWidth - window.innerWidth);
  console.log('extra scroll width:', overflow); // should be 0
  await browser.close();
})();
```

Check at minimum: 1600×900 desktop **and** 390×844 mobile viewports; all 4
sectors open *and* close cleanly (`#sectorDossierOverlay` loses `.active`
after clicking the close control); `document.documentElement.scrollWidth`
never exceeds `window.innerWidth`; no `pageerror`/console errors across a
full sector-navigation + language-switch pass. `tests/pw_check.js` and
`tests/pw_errors.js` have older examples of this pattern.

## After any UI/content change

1. If `src/portfolio.md`/`src/interface.yaml` changed: `python3
   tools/build.py` then `node tools/verify.js`.
2. Run a Playwright regression pass (above) — desktop + mobile, all sectors,
   all languages.
3. Update `HANDOFF.md`'s changelog with what changed and why (short bullets,
   dated) — it's the source of truth for the next session, not commit
   messages alone.
4. Commit and push — this repo's standing instruction is to always commit
   and push to `master`/`main` after finishing a unit of work here, not to
   leave changes uncommitted.
